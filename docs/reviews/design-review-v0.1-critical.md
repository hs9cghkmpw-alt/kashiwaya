# かしわや 店舗管理システム 設計激辛レビュー v0.1

## 総評

**現状は「良い構想」だが、実装開始可能な詳細設計ではない。**

要求・業務・アーキテクチャの3文書としては方向性が揃っている。一方、実店舗で金銭を扱うシステムとして見ると、現段階では重要な業務ルール、データ不変条件、障害復旧、認証、印刷、税計算、注文競合、例外系が未定義である。

現状のままClaudeに実装させると、Claudeが不足仕様を勝手に補完し、後からDB/API/UIを作り直す可能性が高い。**実装開始は保留。詳細設計を先に行う。**

## 重大度 S: 実装前に必ず解決

### S-01 伝票モデルが「1卓=1伝票」に寄りすぎている

現在の仕様は来店単位・テーブル単位を前提としているが、実店舗では席移動、合席、伝票分割、代表会計、別会計、人数変更などが発生し得る。

最低限、以下を仕様化する。

- 1テーブルに複数伝票を許すか
- 1伝票を複数テーブルへ移動できるか
- テーブル移動
- 合席
- 伝票分割
- まとめ会計
- 個別会計
- 会計後の訂正

初期版で非対応にする場合も、**「非対応であることを明示し、操作時に安全に拒否する」**必要がある。

### S-02 注文の状態モデルが粗すぎる

`SUBMITTED -> ACCEPTED -> PREPARING -> SERVED` だけでは足りない。

最低限、以下を分離する必要がある。

- 注文受付状態
- 調理状態
- 提供状態
- 取消状態
- 売切れ/欠品による差し戻し
- 店員注文と客注文の発生元

特に「注文全体」と「注文明細」の状態を分ける必要がある。焼き鳥3本のうち2本だけ提供済み、のような部分進捗を表現できないと現場で破綻する。

### S-03 金額計算仕様が未確定

金額をDB上で整数円として扱うこと、税率、税込/税抜、端数処理、割引、サービス料等を明文化する必要がある。

特に、以下を決めないまま実装してはいけない。

- 金額の単位
- 税込価格表示か
- 消費税の計算単位
- 端数処理方法
- 税率が異なる商品の扱い
- 将来の軽減税率
- 値引き
- 返品/返金

**浮動小数点で金額計算しない。**

### S-04 「現金会計」の会計確定トランザクションが未定義

「現金を受領→会計確定→伝票クローズ」の間でアプリが落ちた場合を定義していない。

会計確定はDBトランザクションとして原子的に設計する必要がある。

二重クリック・ブラウザ再送・通信再送による二重会計を防ぐため、冪等性を会計にも適用する。

### S-05 SQLiteバックアップ方式が未定義

「DBファイルをコピー」だけでは危険。営業中のSQLiteを単純コピーする方式は採用しない。

SQLiteのバックアップAPIまたは安全なバックアップ手順を設計し、バックアップの整合性検証と復元テストまで仕様化する。

### S-06 Note PCが単一障害点

Note PCが故障すると全システムが停止する。

最低限、以下を定義する。

- Windows自動起動
- アプリ自動起動
- Windows更新による再起動への対応
- スリープ無効化
- 電源断復旧
- バックアップ先
- 代替PCへの復旧手順
- UPSを導入するか

## 重大度 A: 実装前に仕様化推奨

### A-01 QRの「テーブル番号だけ」はセキュリティモデルとして弱い

静的QRのURLにテーブル番号だけを入れると、別テーブルURLを推測できる可能性がある。

顧客セッションを「この端末がこのテーブルの注文を行っている」と安全に扱う仕組みが必要。

ただし顧客情報を取る必要はない。短寿命の注文セッションや署名付きテーブルトークン等で十分。

### A-02 客側からの注文を無条件に伝票へ入れる仕様は危険

QRを読み込んだ人が本当にその席の客なのかを確認する必要がある。

最低限、店員が「入店/伝票開始」を行い、その後QR注文を許可する状態を設計する。

### A-03 「店員が注文を受付」の意味が曖昧

客が注文確定した瞬間に厨房へ飛ばすのか、店員が承認してから厨房へ送るのかを決める必要がある。

実店舗では「客注文→厨房直送」と「店員確認→厨房送信」の両方に運用上の違いがあるため、設定可能にする価値がある。

### A-04 メニューのバリエーションが未定義

焼き鳥店では以下のような仕様が発生し得る。

- 塩/タレ
- 数量
- 大小
- トッピング
- 焼き加減
- 同一商品の個別指定
- 備考

`menu_items`だけでは不足する可能性が高い。商品オプションモデルを検討する。

### A-05 注文備考が必要

「別皿」「後で」「塩多め」など、現場で必ず発生する自由記述を考慮する。

ただし顧客自由記述をそのまま厨房へ表示するとUIを壊す可能性があるため、文字数制限・危険文字処理・表示位置を仕様化する。

### A-06 ラストオーダーと営業状態

`営業中/停止`だけでは足りない。

最低限、

`準備中 -> 営業中 -> ラストオーダー -> 新規注文停止 -> 会計のみ -> 締め`

を検討する。

### A-07 印刷が「最適方式を後で決定」では遅い

厨房伝票・レシート・領収書は実機依存が大きい。

使用予定プリンターを先に確認し、印刷キュー、再印刷、印刷失敗、紙切れ、二重印刷の扱いを決める。

### A-08 印刷を正本にしない方針は正しいが、厨房運用を詰める必要がある

画面が正本でも、厨房が紙中心なら紙が実務上の作業媒体になる。

「印刷成功済み」「印刷失敗」「再印刷済み」を管理し、同じ注文が二重調理されない仕組みが必要。

### A-09 認証設計が抽象的

STAFF/MANAGER/ADMINの役割だけでは足りない。

- PINかパスワードか
- 共用アカウントを許可するか
- 店員交代
- セッションタイムアウト
- 管理操作時の再認証
- 会計取消時の権限

を定義する。

### A-10 監査ログは「ログを残す」だけでは不十分

監査ログ自体を改変できない設計が必要。

少なくとも、対象ID、操作種別、実行者、時刻、変更前、変更後、理由、端末を記録する。

## 重大度 B: 詳細設計で詰める

### B-01 テーブル状態と伝票状態を混同しない

テーブルは空席でも伝票が未クローズ、または伝票はクローズ済みでもテーブル清掃中、など現場状態は分離した方がよい。

### B-02 日次締めの「営業日」を定義する

深夜営業を想定すると、暦日0:00で売上を分けるのか、営業開始から閉店までを1営業日とするのかが重要。

### B-03 現金出金に承認ルールが必要

誰でも出金できると監査上弱い。少なくとも高額出金や管理者限定出金を検討する。

### B-04 差異ゼロを締め条件にしない方がよい

現金差異があっても営業日を締められないと、現場が止まる可能性がある。

「差異確認済み」という状態と「差異ゼロ」は分ける。

### B-05 レシート/領収書の再印刷

会計済み伝票から再印刷できる必要がある。再印刷自体を監査ログに残す。

### B-06 バックアップの世代管理

「日次バックアップ」だけでは、破損した状態をバックアップしてしまった場合に弱い。

世代数、保存先、保持期間、バックアップ成功確認、復元テストを定義する。

### B-07 ネットワーク構成がまだ概念図

実際のルーター、SSID、IP固定、DHCP、名前解決、顧客ネットワークから店舗サーバーへの到達制御まで決める必要がある。

### B-08 店舗サーバーのURLをどうするか

IP直打ちは運用上つらい。ローカルDNS、mDNS、固定IPなどから選択する。

### B-09 メニュー変更履歴

価格変更だけでなく、販売開始/停止、カテゴリ変更、名称変更も履歴管理する。

### B-10 データ削除ポリシーがない

売上・会計・監査ログは原則削除不可とし、論理無効化や保存期間を定義する。
