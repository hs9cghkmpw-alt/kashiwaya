# かしわや 店舗管理システム アーキテクチャ設計 v0.1

## 1. 全体構成

```text
                         店舗LAN / Wi-Fi
                                |
              +-----------------+------------------+
              |                                    |
       客スマートフォン                         店舗端末
              |                            +-------+-------+
          QR注文                           |       |       |
              |                           POS    厨房    管理
              +---------------+-----------+       |       |
                              |                   |       |
                              v                   v       |
                       +-------------------------------+
                       | Note PC                       |
                       |                               |
                       | Web UI / FastAPI              |
                       | SQLite                        |
                       | Print / Export / Backup      |
                       +-------------------------------+
```

## 2. 配置方針

Note PCを店舗内サーバーとして常時稼働させる。顧客・店員・厨房端末はブラウザで店舗アプリへ接続する。

インターネットは必須ではない。外部接続はアップデート等の管理用途に限定し、通常営業データを外部サービスへ送信しない。

## 3. ソフトウェア構成

### Backend

- Python
- FastAPI
- SQLAlchemy
- SQLite
- Pydantic
- WebSocket（リアルタイム通知が必要な画面）

### Frontend

Webアプリ方式を基本とする。顧客、POS、厨房、管理画面を同一バックエンド上のWeb UIとして提供する。

フロントエンドはTypeScript系SPAを基本候補とする。最終フレームワークは実装前レビューで確定する。

### 印刷

Windows側のローカルプリンターを利用する。厨房伝票・レシート等はプリンター機種を確認後、最適な印刷方式を決定する。

## 4. データベース方針

SQLiteを単一店舗の正本データベースとする。

主要エンティティ候補:

- tables
- menu_categories
- menu_items
- staff
- shifts
- orders
- order_items
- order_events
- payments
- cash_sessions
- cash_movements
- daily_closings
- print_jobs
- notifications
- audit_logs
- system_settings

## 5. データ整合性

以下を特に保証する。

- 注文明細は存在する伝票にのみ紐付く。
- 会計金額は伝票明細から算出可能である。
- 会計確定後の明細直接更新は禁止する。
- 価格は注文明細へスナップショット保存する。
- 現金会計は預かり金以上の金額でのみ確定可能。
- 釣銭はサーバー側で再計算する。
- 同一注文の二重送信を冪等性キー等で防止する。
- 日次締め済み期間の直接更新を禁止する。

## 6. 状態管理

### テーブル

`EMPTY -> OCCUPIED -> PAYMENT_PENDING -> EMPTY`

### 伝票

`OPEN -> CHECKOUT_PENDING -> PAID -> CLOSED`

### 注文

`SUBMITTED -> ACCEPTED -> PREPARING -> SERVED`

取消が必要な場合は削除ではなく取消状態/イベントを使用する。

## 7. 権限

最低限、以下を分離する。

- STAFF
- MANAGER
- ADMIN

顧客端末から管理APIへ到達できないよう認可を実装する。顧客APIは注文に必要な最小機能だけを公開する。

## 8. ネットワーク分離

可能であれば、顧客向けWi-Fiと店舗管理端末を分離する。ルーターがVLAN/SSID分離に対応している場合は、顧客側から管理画面・管理APIへ到達できない構成とする。

ただし顧客注文は店舗アプリの必要な注文エンドポイントへ到達できる必要があるため、実ネットワーク構成は導入予定ルーターの仕様を確認して決定する。

## 9. バックアップ

日次バックアップに加え、重要処理前後のDBスナップショットを検討する。バックアップファイルは営業DBとは別の保存先へ置く。

復旧手順をコードだけに依存させず、運用文書として保持する。

## 10. 障害設計

### アプリ停止

Note PC上でサービス再起動可能とする。

### DB障害

直近正常バックアップから復旧する。

### LAN障害

紙伝票・手動会計へ切替する。

### 印刷障害

画面表示を正本とし、印刷なしでも会計処理を継続可能とする。ただし必要な帳票は後から再印刷可能とする。

## 11. セキュリティ

- 管理画面は認証必須。
- パスワードは平文保存しない。
- 顧客側から他テーブルの伝票を参照できないようにする。
- 注文・会計・締め操作はサーバー側で権限検証する。
- 管理操作を監査ログに残す。
- 秘密情報をGitへコミットしない。

## 13. 設計原則

1. 店舗LANファースト
2. オフライン耐性
3. 現金会計の正確性
4. 監査可能性
5. 変更履歴の保持
6. 現場操作の単純化
7. 復旧可能性
8. 外部サービスへの依存最小化
